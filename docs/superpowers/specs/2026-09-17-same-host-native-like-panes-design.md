# Same-host native-like panes design

Date: 2026-09-17

## Goal

Make 2–9 panes behave more like independent browser tabs when every pane uses the exact same hostname, while keeping all panes simultaneously visible inside the existing Focus Multi View grid.

Only `focus-multi-view-chrome-xtenstion` may change. `ai-chatweb-supporter` and other third-party extensions remain unmodified.

## Constraints

- The grid remains iframe-based; Chrome does not expose arbitrary native tab surfaces that can be embedded as 2–9 interactive panes.
- A third-party extension whose content scripts only run in the top frame cannot be forced by Focus Multi View to run inside these iframes.
- Same-host matching is exact hostname matching, not registrable/base-domain matching. For example, `app.example.com` and `docs.example.com` are different hosts.
- Enhanced behavior requires runtime host permission for each URL scheme currently used by that exact hostname, for example `https://chatgpt.com/*`.
- Runtime permission requests must occur from an explicit user gesture.
- If permission is denied or enhanced attachment fails, the workspace must continue in the existing basic iframe mode.

## Selected approach

Use an enhanced same-host iframe runtime.

The existing grid continues to own pane layout and iframe creation. When all active panes resolve to the same exact hostname and the needed host permission has been granted, a background service worker tracks the corresponding subframes and injects a lightweight Focus-owned bridge into each matching pane frame.

Each pane becomes a logical tab identified by Focus `paneId` plus Chrome frame/document identity. This gives Focus independent navigation tracking, focus, reload, back/forward commands, title/URL state, popup routing, and lifecycle tracking without changing the external site or another extension.

## Mode selection

The grid recalculates eligibility whenever panes are added, removed, or navigate.

A workspace is same-host eligible when:

1. there are at least 2 panes;
2. every pane has a parseable `http:` or `https:` URL; and
3. every pane has the exact same `URL.hostname`.

Enhanced mode becomes active only when the workspace is eligible, all required host permissions are granted, and the frame registry maps the panes to live subframes.

If any condition stops being true, enhanced mode is disabled and the current iframes keep working in basic mode. If all panes later become eligible again and permission already exists, Focus may re-enable enhanced mode without rebuilding the workspace.

If permission for a newly encountered same hostname is missing, the grid shows an **Enable enhanced mode** action. The permission request is made only when the user clicks that action.

The existing compatibility/header-rewrite mode remains independent. Granting same-host permission must not enable compatibility rewriting automatically.

## Permission flow and manifest

Keep the existing broad optional host declaration:

```json
"optional_host_permissions": ["http://*/*", "https://*/*"]
```

Add the minimum extension permissions required for the enhanced runtime:

- `scripting`
- `webNavigation`

Add a Manifest V3 background service worker.

### Initial launch

The popup already has the Launch user gesture and knows all requested URLs before creating the grid tab. If those URLs are same-host eligible, Launch may request the exact required host pattern(s) before creating the grid. For ordinary HTTPS pages this is one pattern, for example:

```text
https://chatgpt.com/*
```

If same hostname URLs use more than one scheme, request only the scheme patterns actually present, for example both `http://example.com/*` and `https://example.com/*`.

If the user denies the request, Launch continues and opens the normal basic iframe grid.

### Later navigation

The grid may query existing permission at any time, but it must not trigger a new permission prompt automatically after navigation. If panes later converge on a hostname whose permission is missing, the user must click **Enable enhanced mode** to request it.

Focus never requests all optional hosts at once.

## Pane identity

Each pane gets a cryptographically random runtime `paneId` generated by Focus Multi View.

The iframe name becomes:

```text
focus-pane:<paneId>
```

The name survives ordinary same-browsing-context navigation and gives the injected bridge a bootstrap Focus identity without modifying the destination URL.

The page can technically mutate `window.name`, so it is not authoritative browser identity. Registration uses these rules:

- `paneId` must be one of the currently unbound pane IDs declared by the owning grid session;
- a live pane ID may be claimed by only one frame/document at a time;
- after binding, that pane accepts messages only from the bound Chrome sender identity until a validated navigation replaces its document;
- duplicate or conflicting claims are rejected.

Chrome-derived sender data is authoritative:

```text
sender.tab.id
sender.frameId
sender.documentId
```

The bridge may report its `paneId`, URL, title, and focus state. The background validates those reports against the owning Focus grid tab and current binding.

## Components

### 1. Grid same-host session controller

The grid remains the authority for:

- pane list;
- pane IDs;
- layout and resizing;
- add/remove pane operations;
- current pane URLs;
- same-host eligibility;
- permission status and the user-triggered enable action;
- rendering native-like pane controls.

It opens a logical session with the service worker and supplies the active pane IDs and eligible hostname. The service worker never invents panes on its own.

### 2. Pane bridge

Add a packaged bridge script, for example:

```text
src/pane/bridge.js
```

The service worker injects it into an eligible pane frame by specific `frameId` after navigation commit.

Responsibilities:

- parse `window.name` and obtain the bootstrap `paneId`;
- report URL and `document.title`;
- report focus/activation signals;
- listen for Focus commands scoped to that frame;
- execute `history.back()` and `history.forward()`;
- report SPA URL/title changes using `popstate`, `hashchange`, and a small history API hook;
- re-report state after relevant title changes without running a high-frequency polling loop.

The bridge must not implement site-specific ChatGPT/Claude/Grok behavior.

### 3. Background frame registry

Add a service worker plus focused modules such as:

```text
src/background/service-worker.js
src/background/frame-registry.js
src/background/popup-router.js
```

Registry shape:

```text
outerTabId -> paneId -> {
  frameId,
  documentId,
  url,
  title,
  hostname,
  loading,
  focused
}
```

The registry listens to `webNavigation` events and bridge registration messages.

A validated new document replaces the previous `documentId` for that pane. Messages from stale documents must be ignored.

When the outer grid tab closes, its registry state is discarded.

### 4. Pane controls

Keep the existing draggable pane-control pill and xAI styling.

In enhanced mode, add native-like actions:

- Back
- Forward
- Reload
- URL field
- Open in native tab
- Close

Back and Forward invoke history operations inside the targeted pane bridge. Chrome does not expose iframe history depth, so the first version does not claim authoritative `canGoBack`/`canGoForward`; commands are safe no-ops when there is nowhere to go.

Reload remains targeted to the pane iframe.

Open in native tab creates a real Chrome tab using the pane's current URL. This is the explicit path for normal top-frame extension behavior, including extensions such as `ai-chatweb-supporter`.

## Same-host popup routing

Selected behavior: when a pane opens a new browsing target through `target="_blank"` or `window.open()`, prefer a new Focus pane.

Use `webNavigation.onCreatedNavigationTarget` and its `sourceTabId` + `sourceFrameId` to map the originating frame back to a Focus pane.

Decision rules:

1. If the source frame is not registered to an active Focus session, ignore it.
2. If the target hostname exactly matches the session hostname and the grid has fewer than 9 panes:
   - ask the grid to create a new pane with the target URL;
   - after the grid acknowledges creation, close the temporary Chrome tab created by the popup.
3. If the target hostname matches but the grid already has 9 panes, leave the target as a normal Chrome tab.
4. If the target hostname differs, leave it as a normal Chrome tab.
5. If target URL parsing fails or the grid does not acknowledge in time, leave the native tab untouched.

A new pane created by popup routing is allowed even when enhanced permission for the target scheme is missing, because it is still the same hostname. In that case the workspace remains usable but enhanced mode waits for an explicit user permission action before attaching to that scheme.

The background must not close a popup tab until the grid confirms that the new pane was created. This prevents losing navigation when the workspace is closing, full, or unavailable.

## Navigation and lifecycle flow

### Initial launch

1. Popup validates launch URLs and computes exact-host eligibility.
2. On the Launch click, if eligible and permission is missing, request only the required current scheme/hostname pattern(s).
3. Whether granted or denied, popup stores launch URLs and creates the Focus grid tab as today.
4. Grid creates panes and stable pane IDs.
5. Grid registers a same-host session with the service worker when permission is available.
6. `webNavigation` observes matching subframe commits.
7. Service worker injects the bridge into each matching frame.
8. Bridge reports bootstrap `paneId`; sender metadata supplies frame/document identity.
9. Registry validates and binds pane to frame, then notifies the grid that enhanced controls are ready.

### Normal navigation

1. A pane navigates or performs SPA history navigation.
2. `webNavigation` and/or the bridge reports the new URL/document state.
3. Registry validates the current document.
4. Grid updates the pane URL/title state.
5. Grid re-evaluates exact-host eligibility and permission status.

### Cross-host navigation

If one pane leaves the common hostname, the session falls back to basic mode immediately. Existing panes remain loaded. No host permission is automatically requested for the new mixed set.

If all panes later converge on one exact hostname, the grid reuses existing permission if available; otherwise it exposes **Enable enhanced mode** for a user-triggered permission request.

## Focus semantics

A pointer/focus interaction inside a pane should mark that pane as the active logical pane. The bridge reports focus and pointer activation to the background/grid.

The active pane is used for keyboard commands that are intentionally pane-scoped. Existing global grid controls remain global.

No attempt is made to change Chrome's actual browser-tab selection: all panes still live inside one outer Chrome tab.

## Compatibility with `ai-chatweb-supporter`

Focus Multi View does not modify, inject, proxy, or copy `ai-chatweb-supporter` code.

The latest checked `ai-chatweb-supporter` branch is `master`, and its content scripts are not configured to run in arbitrary subframes. Therefore enhanced Focus panes cannot make that extension behave as though each iframe were a native top-level tab.

The supported integration path is:

- work inside Focus panes using Focus's enhanced native-like controls; and
- use **Open in native tab** when the user needs ordinary top-frame extension integration.

No cross-extension messaging dependency is introduced.

## Security model

Treat content-frame messages as untrusted.

The service worker must:

- derive `tabId`, `frameId`, and `documentId` only from Chrome sender/event metadata;
- verify the outer tab is a registered Focus grid session;
- verify the reported `paneId` belongs to that session and is not already bound to another live frame;
- verify the frame hostname equals the active exact hostname before injection or privileged routing;
- ignore stale `documentId` registrations after navigation replacement;
- never accept an arbitrary frame ID or tab ID supplied by page script;
- never inject into unrelated tabs or frames;
- never close popup-created tabs until pane creation is acknowledged.

The bridge exposes no general privileged API to the host page.

## Failure behavior

Enhanced mode must be opportunistic.

Fall back to basic mode, without destroying panes, when:

- host permission is denied;
- a host is not frameable;
- script injection fails;
- the service worker restarts and mappings are temporarily absent;
- a frame/document becomes stale during navigation;
- the session becomes mixed-host;
- popup routing cannot safely identify or hand off a target.

After a service-worker restart, the grid should re-register its session. Eligible live frames may be reinjected/rebound, and normal future navigation commits also rebuild mappings.

## Performance requirements

- Preserve the current deferred splitter-resize implementation.
- Do not resize iframes continuously during splitter drag.
- Avoid per-pane high-frequency polling.
- Use event-driven `webNavigation` plus bridge history/title events.
- Keep bridge code small and site-agnostic.
- Registry lookups should be keyed maps by tab/frame/pane rather than scanning all panes on every event.

### Static tests

Verify:

- manifest contains `scripting`, `webNavigation`, and a background service worker;
- existing optional host permissions remain optional;
- bridge/background files are packaged;
- 2–9 pane support remains;
- template CRUD remains;
- draggable pane controls remain;
- deferred splitter-resize behavior remains;
- compatibility mode is not implicitly coupled to same-host permission.

### Manual browser verification

1. Open 2 same-host panes, grant permission from Launch, and confirm enhanced mode attaches.
2. Deny permission from Launch and confirm the basic grid still opens.
3. From an already-open grid, converge panes on a new same hostname and confirm permission is requested only after clicking **Enable enhanced mode**.
4. Confirm multiple panes register independently and show enhanced controls.
5. Repeat with 9 panes.
6. Navigate panes independently, including SPA navigation.
7. Test Back, Forward, Reload, Close, and URL navigation per pane.
8. Test Open in native tab.
9. Trigger `target="_blank"`/`window.open()` on the same host and confirm a new Focus pane is created when below 9 panes.
10. At 9 panes, confirm the popup remains a normal Chrome tab.
11. Trigger a cross-host popup and confirm it remains a normal Chrome tab.
12. Navigate one existing pane cross-host and confirm graceful fallback to basic mode.
13. Return all panes to one hostname and confirm enhanced mode can resume when permission exists.
14. Test same-host mixed `http:`/`https:` URLs and confirm only missing scheme permission requires a user action.
15. Reload the extension/service worker and confirm the session can recover.
16. Verify splitter resizing remains smooth and does not regress to continuous iframe relayout.

## Out of scope

- Modifying `ai-chatweb-supporter` or any third-party extension.
- Making top-frame-only third-party content scripts execute inside Focus iframes.
- Site-specific AI provider automation.
- Embedding actual Chrome native tab surfaces in the grid.
- Base-domain/subdomain grouping.
- Synchronizing cookies or sessions beyond normal browser same-profile behavior.
- Pretending to expose reliable iframe history depth when Chrome does not provide it.

## Success criteria

The feature is complete when same-host workspaces can opt into an exact-host enhanced mode in which each iframe has a stable logical pane identity, independent navigation/focus state, native-like pane controls, safe same-host popup-to-pane routing, user-gesture-scoped exact-host permission handling, and graceful fallback to the existing basic grid, with no changes required in `ai-chatweb-supporter` or other extensions.
